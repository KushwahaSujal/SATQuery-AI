SatQuery AI Design System v2.0

A console for reading the Earth by conversation.

SatQuery is not a chatbot with pictures attached. It is an analysis workspace where the imagery is the subject, the conversation is the instrument, and every claim arrives with the evidence that produced it. This document is the complete visual, interaction, and implementation specification for that product.

01

Principles

Six rules that settle arguments. When a design decision is unclear, the answer is whichever option serves the principle higher on this list.

1 · The scene owns the attention

Reference chat UIs centre a column of bubbles. That is right when text is the subject. Here the imagery is the subject, so it gets the stage and everything else arranges around it. No panel may exceed the viewport in visual weight.

Test: cover the image. If the screen still makes sense, the layout is wrong.

2 · Colour is data, not decoration

Sky blue is always optical. Violet is always SAR. Green is always gain, rose always loss. A hue never appears for visual interest alone — if you want emphasis without meaning, use weight, size, or space.

Test: can you name the data meaning of every coloured pixel on screen?

3 · Evidence ships with every claim

An answer is incomplete without the chain that produced it, the parameters used, the confidence, and a path back to the pixels. The trace is part of the reply, not a debug drawer.

Required by the brief: auditable execution summary.

4 · Machine values look like machine values

Geist Mono is reserved for what was measured or emitted by a system: coordinates, CRS, GSD, bands, areas, model IDs, timings, confidence. Inter carries everything a person reads as language.

Test: no prose in mono, no measurement in sans.

5 · Refusal is a design surface

Incompatible inputs are the normal case, not the exception. The system names the specific mismatch, the specific threshold it missed, and the specific action that fixes it. It never says "invalid input".

Every failure state has at least one recovery button.

6 · Motion only where something moved

The compare handle, a mask resolving, a trace step completing, a panel opening. No entrance animations, no hover lifts, no gradient drift. Motion that does not describe a change is noise on top of noisy data.

Budget: nothing animates longer than 420ms.

Rules

  • Measure. Body prose caps at 68 characters. The conversation rail is 364px precisely so 13/21 lands near that without a max-width override.
  • Numbers. Tabular figures on every mono run (font-variant-numeric: tabular-nums) so values in the stat strip do not jitter when they update.
  • No all-caps. Section labels use 10.5px Inter 600 in text/muted, sentence case. Uppercase tracking is reserved for nothing.
  • Never italic. Emphasis is carried by weight and colour; italic Inter at 13px on a dark ground loses too much stroke contrast.
  • Truncation. File names and session titles truncate with an ellipsis at the end and expose the full string in a native title attribute.

07

Motion

Four durations, three curves, and a hard rule: motion describes a change the user caused or the system made. Nothing animates to look alive.

TokenValueCurveUsed for
d-fast120mseaseHover, focus, chip and button colour
d-base180mseasePanel open, trace expand, tab switch
d-slow280mseaseSheet slide, modal entry, meter fill
d-scene420mseaseOverlay mask fade-in, view mode change
easecubic-bezier(.2,.8,.2,1)—Default for everything entering
ease-incubic-bezier(.4,0,1,1)—Things leaving the screen
ease-springcubic-bezier(.34,1.3,.64,1)—Compare handle release only

Named interactions

  • Compare drag. The handle follows the pointer with zero delay — no easing during drag, easing only on keyboard step. Arrow keys move it 2% per press, Shift+Arrow 10%, Home/End to the edges.
  • Mask reveal. When a change mask finishes computing it fades in over 420ms with the stroke arriving first (0–180ms) and the fill following (180–420ms). This reads as the boundary being found, then filled.
  • Trace step completion. The pending index swaps to a check with no transition; the row's left edge flashes accent at 30% for 180ms. No slide, no height animation — the block must not reflow while the analyst is reading.
  • Streaming answer. Text appears token-by-token with no cursor animation. The trace above it stays pinned; the thread auto-scrolls only if the analyst is already within 40px of the bottom.
  • Reduced motion. Everything above collapses to instant. The mask appears at full opacity, the handle jumps, the spinner becomes a static ring with a text label. Nothing is lost, only the timing.

10

The shell

Three columns with fixed proportions. Sessions and inputs on the left, the stage taking everything left over, the conversation and trace on the right. The stage never falls below 560px — below that viewport width the aside becomes a bottom sheet.

Rail · 212px

Session history, the current session's input files, and a live list of whatever the analysis produced — detected regions, change classes, extracted objects. Selecting an item highlights it on the stage.

Stage · fluid

Tabs for view modes, the viewport itself, and a stat strip when the analysis produces scene-level numbers. This column is the product.

Aside · 364px

The thread, the traces attached to each answer, and the composer. Scrolls independently. Never contains controls that affect the stage — those live on the stage.

Out of scope

Questions the system cannot ground in the imagery are declined by naming what it can do instead — never with a generic apology.

Charts, when they appear

  • Class area comparison — horizontal bars, one row per class, gain and loss on a shared zero axis. Never a pie; proportions of changed area are read comparatively, not as a whole.
  • Time series — only when more than two acquisitions exist. Single line, 1.5px, points at each acquisition, mono axis labels.
  • Band histogram — stacked translucent fills in the actual band colours where they map to visible wavelengths, grey where they do not.
  • No gridline below 20% opacity, no chart junk, no drop shadows on data marks, and the value is always printed as well as plotted.

Rules

  • Sentence case everywhere, including buttons and headings. No title case, no all caps.
  • An action keeps its name through trigger, dialog, and confirmation: Export report → Export report → Report exported.
  • Units always attached, always with a thin space: 4.2 km², 0.65 m, 2.41 s. Areas to one decimal, confidence to two, timings to two.
  • Numbers lead the sentence when the number is the answer. "Increased — by 4.2 km²" beats "Yes, the built-up area has increased, and the amount is 4.2 km²".
  • Never use "simply", "just", "easily", or an exclamation mark. Nothing here is simple and the analyst knows it.
15

Accessibility floor

Non-negotiable. A change map that only works for trichromats is not a change map — it is a picture of one.

  • Colour is never the only channel. Gain and loss masks carry opposing 45° hatch patterns. Sensor chips carry the word as well as the hue. Confidence carries the number as well as the bar.
  • Contrast. Body text ≥4.5:1, large text and UI borders ≥3:1, every combination audited in the table in section 03 for both themes.
  • Focus. A 3px accent ring on every interactive element, never removed, visible against all four surface depths.
  • Keyboard. The compare handle is a slider with arrow, Shift+arrow, Home and End. View tabs are a roving tabindex. The viewport pans with arrows when focused and zooms with + and −.
  • Screen readers. Every change map has a text summary conveying everything the colours do — class, direction, magnitude, location. The trace is a semantic ordered list. Streaming answers use aria-live="polite", the trace uses aria-live="off" so it does not interrupt.
  • Targets. 44×44 minimum on touch; 30×30 with 8px spacing on pointer. Point detections get a 12px hit area regardless of rendered size.
  • Motion. prefers-reduced-motion collapses every transition to instant and replaces the pulsing step indicator with a static ring plus text.
  • Zoom. Layout holds to 200% browser zoom without horizontal scroll at 1280px; the aside becomes a sheet rather than compressing.

Build order

  • 1 · Tokens. Drop the block above into globals.css, wire the Tailwind map, and ban raw hex in review.
  • 2 · Shell. Three-column grid with the stage as a server component and the aside as a client component. Getting column behaviour right before content exists saves a rewrite.
  • 3 · Viewport. The risky part. Tile server-side and serve Cloud-Optimised GeoTIFF — a 4096² raster sent whole will make the demo feel broken no matter how good the models are.
  • 4 · Trace streaming. If the backend emits step events over SSE, the running state comes nearly free and it is the single most convincing thing in a live demo.
  • 5 · Report. Render server-side from the same components so the figures match what was on screen exactly.
Decide these before writing components, not after. Overlay geometry must come back as GeoJSON in the image CRS, not pixel coordinates — pixels break the first time someone zooms. Answers must come back as structured spans with region IDs, not a plain string, or phrase↔box linking cannot be retrofitted. And decide what "confidence" means per task: a model logit and an IoU are different quantities and must not share a meter.

Ship checklist

  • No raw hex anywhere in a component or a screen — every fill and stroke is a variable.
  • Auto layout everywhere children are related; absolute positioning only for overlays on a scene.
  • Every component set has a description stating when to use it and when not to.

  • Responsive variants exist at 768 and 390 for the shell, not just the desktop frame.
