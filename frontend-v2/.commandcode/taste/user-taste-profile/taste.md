# User Taste Profile
- Prefers dark-first design systems with light mode as the counterpart. Dark mode should be the default theme. Confidence: 0.95
- Prefers deep navy (#020D19) over pure black for dark backgrounds, and near-white (#F7FAFD) over pure white for light backgrounds. Confidence: 0.9
- Strongly prefers CSS custom properties (var(--token)) over hardcoded Tailwind color classes for theme-able components. Confidence: 0.95
- Prefers comprehensive semantic token systems covering surfaces, borders, text, shadows, shape/radius, motion, and status colors — organized hierarchically (canvas → workspace → surface → surface-2 → surface-3 → hover). Confidence: 0.9
- Prefers using `next-themes` with `attribute="class"` for dark/light mode switching in Next.js projects. Confidence: 0.9
- Prefers electric blue (#168BFF dark / #087FF5 light) as the primary interaction color, cyan (#00C7D9 / #00AFC5) for AI/analysis accents. Confidence: 0.9
- Uses semantic remote-sensing color coding: Blue=Optical, Violet=SAR, Green=Vegetation/Gain, Red=Change/Loss, Cyan=Water, Amber=Warning. Confidence: 0.95
- Prefers subtle blue glow shadows in dark mode (rather than black shadows) and soft blue-tinted shadows in light mode. Confidence: 0.9
- Prefers very subtle 1px borders with blue-gray tones rather than bold or high-contrast borders. Confidence: 0.9
- Prefers Inter as the primary sans-serif font and Geist Mono for technical/numeric data display. Confidence: 0.9
- Prefers dense but readable UI typography (13px base body, 10-12px for metadata, monospace for technical data). Not oversized. Confidence: 0.85
- Prefers dense professional dashboards over chatbot-style interfaces. Satellite imagery should be the visual hero. Confidence: 0.9
- Expects visualization/satellite image containers to be prominently sized (tall, e.g. h-80 or larger) rather than compact defaults — iteratively pushes container heights up when they feel too small. Wants the imagery to visually dominate its section. Confidence: 0.85
- Prefers gradient accents (e.g. brand gradient #00C9E8 → #087FF5 → #1758D8) restricted to important elements rather than used everywhere. Confidence: 0.85
- Prefers rounded but not excessively rounded corners — uses a stepped radius system (4px→6px→8px→12px→16px→20px). Pills only for status/dataset type badges. Confidence: 0.85
- Prefers Lucide-style outline icons (1.8–2px stroke) for the icon system. Confidence: 0.8
- Provides extremely detailed visual specifications with exact hex values, usage context, and hierarchy descriptions when communicating design requirements. Confidence: 0.95
- When using `next-themes`, applies the mounted-state hydration guard pattern: `const [mounted, setMounted] = useState(false); useEffect(() => setMounted(true), []);` then conditionally applies theme-dependent styles, plus `suppressHydrationWarning` on theme-toggle buttons. Confidence: 0.9
- Expects design token values to match specifications exactly — audits hex values against the spec and flags any deviation, no matter how minor. Confidence: 0.9
- Uses Windows (D:\ paths, cmd commands). Confidence: 0.9
- Builds Next.js 16+ projects with Turbopack, React Query, and TypeScript. Confidence: 0.9
- Strongly prefers "verify first, then implement" workflow — wants libraries/research done before code is touched, and dislikes jumping straight to implementation. Confidence: 0.9
- Strongly dislikes AI-generated-looking UI signals and will audit designs for them ("is the site colors and looking ai genarated designs?"). Specific AI-tells to avoid: overuse of particles, excessive BorderBeam/GlowCard stacking, gratuitous animations, cyan/blue gradient avatars with glow effects, pulse animations, centered hero + card-grid welcome layouts, and gradient hover overlays. Wants professional developer aesthetic — restraint and intentionality over flashy effects (rule of thumb: max 1-2 motion effects per page). For welcome/landing screens, prefers: left-aligned asymmetric headers over centered heroes, flat bordered surfaces without glows/gradients, horizontal action button strips over gradient cards, list-based prompt rows over grids, subtle grid-line background texture, and small monospace uppercase category/brand tags. Confidence: 0.95
- Familiar with the modern React UI library landscape (21st.dev, Magic UI, shadcn/ui, MUI X, Chakra, Superdesign, SmoothUI) and evaluates them critically — prefers copying curated components from Magic UI/shadcn rather than adopting full theming systems (Chakra, MUI) that would conflict with an existing design-token system. Confidence: 0.85
- Communicates requests in casual, abbreviated prose with typos and missing punctuation (e.g. "new analysis have right side ghave some chat design it showing that way when someone click recent chats . understand?"). Tolerates this style — does not require formal requirements docs. Confidence: 0.85
- Expects the right-side chat panel to behave like a real chat UI: collapsible "Recent Chats" history list above the tab strip, persistent sessions in localStorage, working send handlers, message bubbles that render real (not mocked) messages. Wants chat history to be accessible from inside the chat panel itself, not just from a separate /history route. Confidence: 0.85
- Strongly prefers real-data fidelity over polished-looking mocks. When UI affordances exist (chat history, status badges, metrics), the underlying data must come from the real backend pipeline — fake assistant responses, hardcoded meta fields, or setTimeout-based placeholders are unacceptable even temporarily. Would rather defer a feature than ship a misleading one. Confidence: 0.9
- Expects lists and history views (Recent, job lists) to show only meaningful, successfully-initiated items — failed or cancelled entries should be filtered out both client-side and at the API level. Cluttering a history panel with failed attempts feels unprofessional. Confidence: 0.85
- Prefers surgical, additive edits over wholesale rewrites of large files (e.g. a 1476-line analysis page). Acceptable to wrap dead/hardcoded code in `{false && ...}` to preserve it for future wiring rather than deleting it. Confidence: 0.85
- Prefers localStorage-backed stores for client-side persistence (chat history, recent items) with a sensible retention cap (e.g. max 50 sessions) and ISO timestamps for created_at/updated_at. Uses helpers like get/save/create/append/delete with an active-session pointer. Confidence: 0.8
- When migrating from v1 to v2 of a frontend, expects the assistant to study the working v1 codebase as the authoritative reference for backend integration patterns — not just the API docs — and replicate the same wiring in the new version. Confidence: 0.85
- Wants a two-phase UX pattern for analysis workflows: ChatGPT-style centered chat interface for input/interaction, transitioning to a dense dashboard/split-view for results. Chat for submission, dashboard for consumption. Confidence: 0.8
- Wants chat input components to be feature-rich and professional-grade — drag-and-drop file upload, attached image previews with thumbnails, analysis type/action selectors, auto-resize, and keyboard hints. Plain single-line text fields feel undercooked. Confidence: 0.8
- References established products (e.g. "like ChatGPT") as mental models for desired UX patterns — expects assistant to recognize these industry-standard interaction flows and implement them faithfully rather than inventing novel alternatives. Confidence: 0.8
- Communicates UI bugs and issues visually via screenshots rather than describing problems in text — expects the assistant to diagnose what's wrong from the image and fix it without detailed written reproduction steps. Confidence: 0.85
- Reports backend errors by pasting raw server terminal logs/tracebacks without any textual summary or question — expects the assistant to diagnose directly from the trace output and fix without needing a written description. Often appends terse directives like "fix all" inline with the log output, expecting the assistant to identify and resolve all related issues proactively, not just the surface error. Confidence: 0.9
- Provides pre-built React components (full source code) for the assistant to integrate into the codebase, rather than describing what they want built from scratch. Expects the assistant to study the component, adapt it to the project's theme/design tokens, and wire it into the appropriate places. Confidence: 0.85
- Strongly values UX feedback during long-running operations — finds no visual feedback during file uploads to be a bad experience. Expects progress indicators, loading states, and phase labels for any async operation that takes noticeable time. Confidence: 0.9
- Expects visual consistency across all representations of the same data — if a thumbnail shows a split view for a bi-temporal job, the detail/preview panel for that same job must also show a split view. Mismatched representations across views of the same data feel broken. Confidence: 0.85
- Expects any third-party or provided component to be restyled with the project's existing design tokens and color scheme rather than shipped with its default colors. Will explicitly request "make it for my site with colors." Confidence: 0.85
- Provides structured integration instructions with numbered steps, specific dependency lists, and folder placement expectations when introducing new components. Prefers the assistant follow these structural guidelines. Confidence: 0.8
- Prefers destructive/bulk actions (clear history, delete all, etc.) to live only on the dedicated page for that data, not in global navigation chrome like sidebars. Context-specific actions should appear in the context they affect. Confidence: 0.85
- Expects list/history views to support checkbox-based multi-select with bulk delete (select individual items or all, then delete selected) — considers this a baseline "professional" UX pattern for any data management table. Confidence: 0.85
- Prefers rich dropdown/menu styling with SVG icons, category section headers, and active-item checkmarks over minimal compact designs with colored dots and terse labels. Will revert redesigns that strip visual richness in favor of minimalism, even if the minimal version matches a reference implementation. Confidence: 0.85
- When studying v1 as a reference for v2 migration, wants only the functional/backend integration patterns replicated — not v1's visual styling. v2 should retain its own design identity (icons, categories, richer components) even when v1 used a simpler approach. Confidence: 0.85
